# 渗漏水处置业务边界规则（v1.0）

适用模块：渗漏水处置（leak）、设施检修管理（maintenance）、门禁安防运维（access）、运维值班交接（duty）。
本文是这些模块状态流转、字段取值、跨模块回写与权限控制的唯一口径；页面只做渲染，所有判断在数据服务层执行（纯前端仓库对应 `frontend/src/api/` 下的领域服务）。

---

## 1. 字段与取值口径

### 1.1 渗漏处置单字段

| 字段 | 必填时机 | 取值口径 |
| --- | --- | --- |
| 处置编号 | 创建时 | 系统生成，`LEAK-####`，全生命周期不变 |
| 渗漏点位（文字） | 创建时 | 现场描述，如"综合舱 K1+220 左墙施工缝" |
| 点位编码（判重键） | 派工前 | 由点位文字规范化得到，见 §6 |
| 渗漏程度 | **派工前必须有实测值** | 等级枚举，由实测流量/形态判定，见 §1.2；取不到不得填 0 |
| 实测流量(L/min) | 派工前必须有 | 数字；**只有本字段允许出现 0**（干裂缝实测 0.0），且必须同时把"程度状态"记为"已实测" |
| 程度状态 | 系统维护 | `已实测 / 待测（空态） / 中断`，见 §2 |
| 未测原因 | 空态时必填 | 自由文本，如"设备未到场""积水遮挡测点" |
| 中断原因 | 中断时必填 | 自由文本，如"抽水设备故障，测量中断" |
| 采集轮次 | 系统维护 | 首次实测=1，每走一次"重新采集"+1 |
| 处置方式 | 派工时 | 由实测程度带出建议值，可由处置班组确认/修改 |
| 处置班组 | 派工时 | 从班组字典选择，不接受空串 |
| 发现日期 | 创建时 | 业务发生日（YYYY-MM-DD），老记录补录也填原始发现日，不填补录操作日 |
| 完工日期 | 完工时 | 现场确认完工当日 |
| 返工原因 | 要求返工动作时必填 | 不填拒绝流转，见 §3 |
| 来源标记 | 系统维护 | `现场实测 / 历史补录`；补录且程度缺项的单子额外带"补录缺项"标记 |
| 补录原值 | 补录时回填 | 原纸质/旧系统仅有的"渗漏部位"原文，原样保留不做推断 |
| 归属单位 / 归口岗位 | 创建时落定 | 按创建人所属单位、岗位写入；**任何人改动记录都不改这两个字段**，见 §8 |
| 最后操作人 | 系统维护 | 每次写操作记录实际操作人，用于审计 |

### 1.2 渗漏程度等级（实测口径）

以现场实测流量为主、形态为辅，统一五级，禁止用"差不多""看着像"等口头描述落库：

| 等级 | 判定口径 |
| --- | --- |
| 无渗漏（干裂缝） | 实测流量 = 0，且表面无湿渍 |
| 湿渍（Ⅰ级） | 流量 0～0.1（不含 0），表面湿润无明水 |
| 慢渗（Ⅱ级） | 流量 0.1～1（不含 1），可见明水、不成线 |
| 快渗（Ⅲ级） | 流量 1～10（不含 10），水流成线 |
| 涌漏（Ⅳ级） | 流量 ≥ 10，涌水/射流 |

处置方式由等级带出建议（无渗漏→封闭观察，湿渍→表面封堵，慢渗→注浆封堵，快渗/涌漏→导流+注浆并提级响应），班组可在该建议基础上确认或加强，不得降级处置。

## 2. 空态、中断与"没有数据不许当 0"

1. **渗漏程度取不到时 → 空态**：`渗漏程度`留空，界面统一显示"待测"（徽标），`程度状态=待测（空态）`，且必须写明`未测原因`。空态不是异常、不是 0，只是"还没测到"。
2. **测量过程中断 → 中断态**：`程度状态=中断`，必须写明`中断原因`；中断态同样不算 0，已采到的半截数据不落正式字段，只记入采集备注。
3. **"没有数据"一律不许当 0**：空、中断、历史缺记三种情况都禁止写入数字 0。0 只能来自现场实测流量字段，并附带实测人/时间；任何用 0 代替"没测到"的保存请求一律拒绝。
4. 空态与中断态各自携带各自的原因，两者互斥、不得混用；状态切换（空态→中断、中断→重新采集）留采集轮次痕迹。
5. 统计口径：空态、中断态不计入任何"程度等级"的分子分母，单独成项展示（待测 X 单 / 中断 X 单），防止待测单被算进"轻度渗漏占比"之类的指标。

## 3. 状态流转与强校验

状态机：

```
待处置 ──派出处置──▶ 处置中 ──确认完工──▶ 已完工
  ▲                   │                    │
  │                   └──要求返工(必填返工原因)──▶ 需返工
  └──────────重新处置（重新采集+派工）──────────────┘
需返工 ──返工完成──▶ 待复核 ──复核通过──▶ 已完工
                    └复核不通过（必填原因）──▶ 需返工
```

硬规则：

1. **处置单不能带空值进入"处置中"**。执行"派出处置"时服务层逐项校验：渗漏程度（已实测）、实测流量、处置方式、处置班组，任一缺失即拒绝，并返回缺项清单（区分"待测""中断"两种原因）；前端置灰按钮仅为体验，服务层必须独立拦截。
2. **要求返工必须填返工原因**，空串/纯空格拒绝；返工原因连同操作人、时间追加进单据履历，不覆盖历史。
3. **重新采集（重试入口）**：打开时默认带出"上一次没取到/中断的那几项"（程度、流量及其状态原因），已实测锁定的字段不重采、不被清空；用户可勾选补采更多项。提交后采集轮次 +1，沿用 §1.2 口径重新判级；全部缺项补齐后才允许再次派工。
4. 非法跳变（如待处置直接完工、已完工再派工）一律拒绝并提示当前状态允许的动作。
5. **同一渗漏点重复派工只派出一次**，判重见 §6。

## 4. 返工结论回写设施检修待办

1. "要求返工"动作成功的同时，在设施检修管理（maintenance）生成/更新一条待办：
   - 状态为新增枚举 **`待复核`**，`pending=true`；
   - 检修编号 `RVW-<处置编号>`（幂等键：同一处置单多次返工只更新同一条，不重复生成）；
   - 检修对象 = 渗漏点位，检修类别固定"渗漏返工复核"，并回写：处置编号、返工原因、返工时间、要求复核时限；
   - 检修班组默认取该处置单的处置班组。
2. 返工完成、复核通过后，该待办随处置单一起闭环（待办关闭、`pending=false`）；复核不通过时待办保持"待复核"并追加不通过原因。
3. 渗漏处置页面与检修页面都能通过处置编号/检修编号互相跳到对方那条记录。

---

## 5. 整改动作回写与安防台账一致、值班清单同步

1. **条数一致（硬不变量）**：返工闭环触发整改动作回写后，
   `设施检修待办中来源=渗漏整改的待复核条数`
   必须与
   `门禁安防台账（access）中"需整改"状态且来源=渗漏联动的条数`
   **逐条 1:1 对应**（关联键 `RVW-<处置编号>`，双向幂等 upsert）。
2. 回写在一个"事务"内完成（本地数据层即一次同步保存）：先算两侧目标集合，差量补/撤后比对，条数对不上则整批拒绝并返回差异明细，不许只成功一半、更不许靠造空记录凑数。
3. **值班清单与台账同步更新**：派出处置、要求返工、返工完成、复核闭环四个动作各向当前班次的值班交接记录（duty）追加一条交接事项（处置编号 + 点位 + 动作 + 时间 + 操作人）；同一(班次,处置编号,动作)幂等，重复点击不产生多条。值班清单上能直接数到与台账一致的未闭环事项数。
4. 页面提供"联动对账"展示：上述两侧条数实时并排显示，不一致时红色告警并列出差异键，不允许静默。

## 6. 判重口径（定）

- **判重字段：点位编码**（不是处置编号，也不是点位文字原文）。点位文字做规范化：去空格/标点、全角转半角、大写化、统一里程桩号写法（`K1+220` 与 `k1+220 `、`K1+220.0` 视为同一编码），编码结构 = `舱室 + 里程桩号 + 部位`。
- **判重窗口：同一渗漏点存在"未闭环处置单"**（状态 ∈ 待处置、处置中、需返工、待复核）即视为在办。
- 命中判重时：
  - 对**在办单再次"派出处置"→ 拒绝**（这是"重复派工只派出一次"的拦截点，返回在办单编号）；
  - **新建环节命中同样拒绝登记新的未闭环单**，强提示"该点位有在办单 LEAK-xxxx（状态）"并引导直接打开在办单继续处置，避免同一点位挂两张待处置单；确属再次渗漏的，待在办单闭环后再登记；
  - 在办单闭环（已完工且复核通过）后，同一渗漏点再次渗漏允许新建，新单与历史单通过点位编码关联，可追溯。
- 点位文字无法规范化出"舱室+桩号"两要素的，点位编码置为待补，禁止派工（先补点位再处置），且不得参与自动判重。

## 7. 存量单与上线前老记录的补录口径（定）

1. **按业务发生日回填，不按补录日**：所有存量/老记录一律使用原始发现日期落"发现日期"，按发现日期分批整批补录（同月一批），补录批次留痕（批次号=补录操作日+批内序号）。
2. **早年只记了渗漏部位、没记程度的补录口径**：
   - 渗漏程度留空、显示"待测"，程度状态记为"待测（空态）"，未测原因统一记 **"历史档案仅登记渗漏部位，无程度观测记录（历史缺记）"**；
   - 来源标记 = `历史补录` + `补录缺项`，原部位原文进"补录原值"字段封存；
   - **不推测、不套默认等级、不写 0**。这类单子派工前必须先走一次现场重新采集，拿到实测值后来源标记转为"现场实测"，补录原值保留可溯。
3. 缺项逐项单独标注来源（如"点位：历史补录；程度：缺项待测"），不允许整单只打一个笼统标记。
4. 上线前的老记录在数据播种/导入时一次性整批补录完成；页面提供"历史补录"批次视图，可按批次、缺项筛选。

## 8. 两处取值打架与权限归属

1. **以现场实测那份为准**：同一指标存在多份取值（历史补录值、台账转抄值、现场实测值）时，以**现场实测**为权威值；服务层保存实测值时，用实测值覆盖展示值并触发下游重算：
   - 渗漏程度按实测流量重判 §1.2 等级；
   - 处置方式建议按新等级重算（班组已确认的处置方式保留人工结论，但低于新等级要求时强制提示升级）；
   - 相关统计卡片、联动待办的整改级别随之重算。
   被覆盖的值进履历可查，不物理删除。
2. **跨单位只读**：会话带归属单位。对非本单位的处置单/待办，页面呈现只读（动作按钮全部隐藏），服务层对任何写动作（派工、返工、重采、完工、复核、编辑）一律拒绝并返回"跨单位只读"；拒绝事件记审计日志。
3. **改动的记录仍归原岗位**：任何编辑、补录、重测都只改业务字段，`归属单位/归口岗位`锁定为创建时的值，不随操作人变化；履历里能看到"谁在什么时候替原岗位补了数据"。
4. 越权提交（含伪造前端状态直接调服务）以后端/服务层拒绝为准，前端隐藏不算授权。

---

## 9. 不变量清单（测试与对账依据）

1. 任意时刻，处置中及之后状态的处置单，渗漏程度与实测流量必不为空、且流量必带"已实测"状态。
2. 系统内不存在"无实测却为 0"的流量值。
3. 一个渗漏点位编码在任一时刻最多对应 1 张未闭环处置单；重复派工请求被拒绝。
4. 每张"需返工/待复核"处置单必有非空返工原因，并恰好对应 1 条 `RVW-` 检修待办。
5. 渗漏联动的检修待复核条数 = 安防台账"需整改（渗漏联动）"条数；值班清单未闭环事项数同源一致。
6. 历史补录缺项单不重采不得派工。
7. 跨单位写操作成功数 = 0；记录的归属单位/岗位永不因编辑改变。
